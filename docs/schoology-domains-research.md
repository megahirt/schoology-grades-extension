# Ask for each school, never every website

Schoology is one web application served on three kinds of address: the shared `app.schoology.com`, free Enterprise subdomains such as `lausd.schoology.com`, and a smaller set of school-owned custom domains such as `schoology.npchristian.org`. The current manifest pattern `https://*.schoology.com/*` covers the first two and misses the third. Parents usually sign in on the shared host while students sign in through district single sign-on on the school's own address. That split is why Northpointe Christian (NPC) families meet both addresses, and why the extension has to cope with more than one site. A page is easy to recognise as Schoology on any domain: asset paths under `schoology_theme`/`schoology_core`, links to `asset-cdn.schoology.com`, the `s_user_login_form` form id, and `x-schoology-server` response headers. **The recommendation is a hybrid.** Keep a short, hand-maintained list of required hosts (`*.schoology.com` plus the custom domains already known, today NPC). For any other school, declare `optional_host_permissions` and call `permissions.request` for that one exact origin, after a user gesture in the popup or the options page, then register the content script for it dynamically. Do not use `<all_urls>`. Two open WebKit bugs shape the Safari build. [Bug 290508](https://bugs.webkit.org/show_bug.cgi?id=290508) makes an optional `*://*/*` declaration badge every site. [Bug 260676](https://bugs.webkit.org/show_bug.cgi?id=260676) drops cookies from extension fetches, which undermines `maybeAutoRefresh` on Safari whichever domain strategy is chosen. Safari should therefore ship without the wildcard optional permission, and its background refresh should run through an open Schoology tab rather than the service worker.

## Three address patterns, one application

PowerSchool's documentation describes two Enterprise options beyond the shared host. A **custom subdomain** (`yourschool.schoology.com`) runs under Schoology's wildcard certificate. A **custom domain** (`learn.yourschool.edu`) requires the school to point a CNAME at `domain-ssl-1.schoology.com` and to apply for an SSL certificate through Schoology, a process that "can take up to three weeks." The same page says neither option is available to customers in Canada ([PowerSchool docs](https://uc.powerschool-docs.com/en/schoology/latest/custom-domains-and-subdomains)). DNS probes on 2026-11-08 matched this. `schoology.npchristian.org`, `lms.lausd.net`, `districtlms.seattleschools.org` and others CNAME to `domain-ssl.schoology.com`, while `lausd.schoology.com` and similar subdomains CNAME to `app.schoology.com`. All of them serve the same Drupal application with the same `/login`, `/grades/grades` and `/parent/grades_attendance` paths, so the extension's parsing code needs no per-school changes. Only its permission to run on each site differs.

Custom domains can be counted, at least roughly. The custom-domain endpoints present PowerSchool-issued multi-SAN certificates. On the test date, the one served for `schoology.npchristian.org` carried 192 names and a second carried 196. Together they list **379 unique school custom domains**. About 62% begin with `schoology.`, followed by `lms.` (41), `elearning.` (23) and `learn.` (15), and most are US K-12 `.org` names. These figures come from `openssl s_client` probes, not a published source. Count 379 as a floor: schools on other certificates, or without SSL, are not included. Subdomains cannot be counted. `*.schoology.com` is a DNS wildcard (a made-up `zzqxnotreal123.schoology.com` also resolves), and the wildcard certificate names no tenants. Subdomains cost nothing to set up, while custom domains take a three-week certificate process. Subdomains are therefore almost certainly the majority of Enterprise tenants, with custom domains in the hundreds. No source gives an exact ratio.

| Pattern | Example | How it is served | Covered by `https://*.schoology.com/*`? | Rough prevalence |
|---|---|---|---|---|
| Shared host | `app.schoology.com` | Basic users and nearly all parent accounts | Yes | Every user can reach it |
| Enterprise subdomain | `christinak12.schoology.com`, `sd25.schoology.com` | CNAME to `app.schoology.com`, wildcard cert | Yes | Most Enterprise tenants (uncountable) |
| Enterprise custom domain | `schoology.npchristian.org`, `lms.lausd.net` | CNAME to `domain-ssl(-1).schoology.com`, shared PowerSchool multi-SAN cert | **No** | At least 379 hosts |

Subdomains do not always behave the same way. `lausd.schoology.com/` redirects to the custom domain `lms.lausd.net`. `npchristian.schoology.com/`, by contrast, falls through to a generic `/login?&school=` page, as a made-up subdomain does. So a school's custom domain is not always reachable through its subdomain, and neither address can be derived from the other.

## Parents use the shared host and students use the school's sign-on

District guidance is consistent here. Seattle sends students through Clever and Microsoft sign-in, and tells parents to use `https://app.schoology.com/login` with access codes from the parent portal ([Seattle Public Schools](https://www.seattleschools.org/Schoology)). Meigs Local sends students to `schoology.meigslocal.org` and parents to `app.schoology.com/login`, with first-time access through "Forgot Password" ([Meigs Local](https://www.meigslocal.org/parents/schoology)). Other districts say parents cannot use the district student/teacher login and must register at `app.schoology.com` with a per-student Parent Access Code ([Mt Vernon CSD](https://www.mtvernoncsd.org/family-community/parent-schoology-accounts), [Christina SD](https://www.christinak12.org/cms/lib/DE50000539/Centricity/Domain/25/SCHOOLOGY%20ACCESS%20for%20parents.pdf)). Mobile-app guides follow the same split: parents choose "log in through Schoology.com" and students choose "Sign in through my school" ([Red Clay SD](https://www.redclayschools.com/students-families/technology-support/schoology/log-in-to-schoology-using-the-ios-or-android-app)).

The reason is identity ownership. Student accounts are provisioned from the district's identity provider (Google, Microsoft, SAML, Clever or ClassLink) and bound to that tenant. Parent accounts are native Schoology email-and-password accounts, and districts tell parents to use the shared host. NPC shows the pattern clearly. On 2026-11-08, `schoology.npchristian.org/` and every protected path on it redirected straight to Microsoft sign-in, whose callback URL is on `app.schoology.com`. The district hosts still serve a local email/password form at `/login`, so a parent could sign in there, but schools do not tell them to.

Two practical consequences follow. First, the session cookie for a custom domain such as `npchristian.org` cannot be shared with `schoology.com`, so each origin needs its own signed-in session. The `multi-domain` branch's rule fits this: follow whichever listed site the family is signed in to, and never swap a parent account for a student account. Whether `*.schoology.com` subdomains share a parent-domain session cookie is unverified. No `Set-Cookie` appeared before login, so checking it needs a signed-in browser. Second, an SSO-only school may never show the login form to a student, so detection cannot rely on login-page markers alone.

**There is no public directory of school addresses.** Discovery has four routes. The first is the school-search autocomplete at `app.schoology.com/login/sso`, which resolves a school name or postal code to a `school_nid` but not to a custom host. The second is district help pages. The third is DNS, where a CNAME to `domain-ssl*.schoology.com` or `domain.schoology.com` identifies a custom domain. The fourth is the SAN lists on PowerSchool's shared certificates. In practice the most reliable source is the family's own browser: the host where the family is signed in is, by definition, the right address. The extension should learn the address from a page the user opens, or from an address the user types, rather than looking it up.

## Asset paths and headers identify Schoology on any domain

The public login page is the same server-rendered page on all four hosts tested (`app.schoology.com`, `lausd.schoology.com`, `lms.lausd.net`, `schoology.npchristian.org`). Each contains `form#s-user-login-form` with `input[name=form_id][value=s_user_login_form]`, the title "Log in to Schoology", 11 to 13 references to `/sites/all/themes/schoology_theme/` and `/sites/all/modules/schoology_core/`, and links to `asset-cdn.schoology.com` for the favicon, the theme CSS and a per-school stylesheet. Custom domains still load assets from that CDN. Pages after login also expose `Drupal.settings.s_common` (user id and CSRF token) and a `window.siteNavigationUiProps` JSON block. That is documented in open-source Schoology tools ([sgy-sgy README](https://github.com/SheepTester/sgy-sgy/blob/main/README.md), [schoology-plus background.js](https://github.com/iahuang/schoology-plus/blob/master/background.js), [BetterSchoology](https://github.com/anli5005/BetterSchoology/blob/main/SchoologyAPI/SchoologyClient.swift)). It was not observed directly, because signing in was out of scope.

At the server, every response on all four hosts carried `x-schoology-server: prod-core-web-…`, `x-schoology-env: deploy` and `content-security-policy: frame-ancestors 'self' *.app.schoology.com`. These headers are the most reliable signal, but an extension can only read them after it has host permission for the origin. Before login the only cookie set is `login_landing_dest`. The session cookie after login is `SESS<hash>`, which is generic to Drupal. Redirects are also telling: protected paths return a 302 to `/login?destination=…` or to the school's SSO handoff at `/login/external_accounts/send/<provider>`.

| Signal | Where it works | Specificity | Cost to an extension |
|---|---|---|---|
| `link[href*="asset-cdn.schoology.com"]`, or a `script[src]` containing `/sites/all/themes/schoology_theme/` or `/sites/all/modules/schoology_core/` | Login page (observed) and, by design, signed-in pages | Very high | One `querySelector` from the isolated world |
| `#s-user-login-form`, `input[name=form_id][value^="s_user_"]` | Login and forgot-password pages | Very high | One `querySelector` |
| Inline script text containing `"s_common"` or `siteNavigationUiProps` | Signed-in pages | Very high | Scan `document.scripts` text, or inject into the MAIN world |
| `x-schoology-server` header | Every response | Definitive | Needs host permission first |
| Host matches `*.schoology.com` | URL only | High, but misses custom domains | Free |
| CNAME to `domain-ssl*.schoology.com`, SAN membership | DNS/TLS | Definitive | Not available to MV3 extensions; build-time only |

Generic Drupal markers (`/misc/drupal.js`, `Drupal.settings`, `#edit-mail`, `SESS*` cookies, the stock `robots.txt`) give false positives and should never count alone. A sensible rule is any one of the first three signals. Content scripts should also exclude Schoology's own non-app hosts (`asset-cdn`, `files-cdn`, `api`, `www`, `developer`, `support` and similar), as Schoology Plus does ([manifest](https://github.com/aopell/SchoologyPlus/blob/develop/src/static/manifest.json)).

## Four permission strategies compared, with Safari decisive

Every building block is available in all target browsers. `optional_host_permissions` is supported from Chrome 102, Firefox 128 and Safari 15.5. `scripting.registerContentScripts` with `persistAcrossSessions` is supported from Chrome 96, Firefox 102 and Safari 16.4. `activeTab` is supported everywhere ([MDN BCD optional_host_permissions](https://github.com/mdn/browser-compat-data/blob/main/webextensions/manifest/optional_host_permissions.json), [BCD scripting](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/scripting.json), [BCD permissions](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/permissions.json)). The real differences are in what users see and how each browser behaves.

**(a) A fixed, hand-maintained list** is what the `multi-domain` branch does. It is transparent, and its install warning stays narrow. Its weakness is updates. In Chrome and Edge, an update that adds a permission warning means "the extension will be disabled until the user accepts the new permission" ([Chrome: Permission warnings](https://developer.chrome.com/docs/extensions/develop/concepts/permission-warnings)). Adding a school is a new host, so each addition probably disables the extension for every existing user. This is an inference: no source showed the exact warning diff. Firefox 127+ adds new hosts on update without showing them ([Extension Workshop](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/)). Safari never grants hosts automatically, so a new entry only makes the extension eligible to ask. Every new school also needs a store release in all four stores. Schoology Plus shows where this leads: its MV2 manifest hard-coded `lms.lausd.net` next to `*.schoology.com` ([old manifest](https://github.com/aopell/SchoologyPlus/blob/develop/old/manifest.json)), and the list never grew beyond its authors' own district.

**(b) Optional `https://*/*` plus a runtime request for one origin** is the pattern Chrome documents for hosts known only at runtime: include `"https://*/*"` in `optional_host_permissions` and request the specific origin "from inside a user gesture" ([Chrome permissions API](https://developer.chrome.com/docs/extensions/reference/api/permissions)). Optional permissions add no install warning and do not trigger re-approval on update. The prompt the user sees names a single site, and the store justification is easy to write: "the user enters their school's Schoology address, and access is requested for that origin only." There are two costs. Detection on an unknown domain must come from the user, either by typing an address or by clicking the extension on the page. And on Safari, **[WebKit bug 290508](https://bugs.webkit.org/show_bug.cgi?id=290508) makes an optional-only `*://*/*` or `<all_urls>` declaration badge the extension and prompt on every site**, including third-party request hosts. It was reported against Safari 18.4, confirmed again in 18.6, and remained NEW with no fix version as of October 2026. A grades extension that asks for access on a family's bank site looks alarming and would undercut the extension's main trust claim. MDN's notes add that in Safari, requesting `*://*/*` "will … automatically prompt the user for access to any visited website" ([BCD permissions](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/permissions.json)).

**(c) `<all_urls>` with a content script that self-activates on Schoology pages** is the easiest to build. Better Canvas uses it, matching `https://*/*` ([manifest](https://github.com/UseBetterCanvas/bettercanvas/blob/main/manifest.json)). It brings the strongest install warning ("Read and change all your data on all websites"), and broad host patterns lengthen Chrome Web Store reviews ([review process](https://developer.chrome.com/docs/webstore/review-process)). It also conflicts with written policy in every store: Chrome requires "the narrowest permissions necessary" and forbids "future proof" requests ([CWS permissions policy](https://developer.chrome.com/docs/webstore/program-policies/permissions)), and Apple's guideline 4.4.2 says Safari extensions "should not claim access to more websites than strictly necessary" ([App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). Even this approach does not secure background refresh. Chrome users can switch an extension to "On click" or "On specific sites", after which background fetches fail "as if the extension's manifest did not include the host permission" ([Chrome runtime host permissions](https://developer.chrome.com/docs/extensions/mv2/runtime-host-permissions)). Approach (c) therefore still needs the check-and-ask logic of (b), while also asking for access to the whole web.

**(d) `activeTab` with `scripting`** adds no install warning in Chrome ([permissions list](https://developer.chrome.com/docs/extensions/reference/permissions-list)). It gives temporary access to the current tab when the user clicks the extension. Apple recommends it as the way to minimise access requests ([Apple: Managing Safari permissions](https://developer.apple.com/documentation/safariservices/managing-safari-web-extension-permissions)), and Apple engineers repeated that advice at WWDC26 ([session 8015](https://developer.apple.com/videos/play/wwdc2026/8015/)). On its own it cannot support `maybeAutoRefresh`, because access ends when the user navigates away. Its value is as the detection half of (b). When the user clicks on an unknown host, the extension runs a fingerprint probe and, if the page is Schoology, offers a one-site grant.

| | (a) Fixed list | (b) Optional + per-origin request | (c) `<all_urls>` | (d) activeTab only |
|---|---|---|---|---|
| Install warning | Narrow | Narrow (optional adds none) | "All your data on all websites" | None |
| Adding a school | Store release; Chrome/Edge re-approval likely | Runtime, by the user | Nothing | Nothing (but no persistence) |
| Store review | Easiest | Easy, with a clear justification | Slowest; policy conflict | Easiest |
| Safari | Per-site prompts still apply | Bug 290508 badging if `*://*/*` declared | Badges/asks everywhere | Clean, temporary |
| Background refresh | Yes (Chrome/Firefox) | Yes once granted | Yes, unless user restricts | No |

The Schoology Plus precedent needs careful reconciliation, because the two notes disagree. One reports that a grep of Schoology Plus's `src/` at commit 85e2e86 found no `permissions.request` or `registerContentScripts` call, and concludes it has no request flow. The other reports that its background script imports fregante's `webext-permission-toggle` and `webext-dynamic-content-scripts`, calls `addDomainPermissionToggle({ reloadOnSuccess: true })`, and gets an "enable on this domain" context-menu item ([background.ts](https://github.com/aopell/SchoologyPlus/blob/develop/src/scripts/background.ts)). Both can be true. The calls live inside the two dependencies, not in Schoology Plus's own source, so a grep of `src/` would miss them. What Schoology Plus lacks is an options page for typing an address and any automatic detection. Its owner said on [issue #82](https://github.com/aopell/SchoologyPlus/issues/82) that support beyond `*.schoology.com` "would need some kind of options page that prompts for permissions." The library internals were not read for this report, so the claim that they call `permissions.request` and `registerContentScripts` rests on their stated purpose and on the `addDomainPermissionToggle` call site. Either way, a mature Schoology extension shipped on the Chrome Web Store with optional `*://*/*` and per-domain toggles, which suggests that declaration does not block a listing.

## Safari's cookie bug breaks background refresh

Whatever the domain strategy, `maybeAutoRefresh` has a Safari-specific problem. **[WebKit bug 260676](https://bugs.webkit.org/show_bug.cgi?id=260676)**, "fetch with credentials should include Cookies associated with host_permissions," has been open since August 2023 and was last modified in August 2026. Extension `fetch(…, {credentials: "include"})` omits SameSite=Lax/Strict cookies. A later comment adds that it also omits SameSite=None cookies unless "Prevent cross-site tracking" is turned off. Apple Developer Forums threads report the same in Safari 18 service workers and non-default profiles. One thread reports that switching to a non-persistent `background.scripts` page restored cookies ([764279](https://developer.apple.com/forums/thread/764279), [776558](https://developer.apple.com/forums/thread/776558), [783498](https://developer.apple.com/forums/thread/783498)). These are developer reports, not Apple statements. Schoology's session-cookie SameSite attribute is unverified and should be checked in DevTools. Safari also requires a per-site grant even for hosts listed in the manifest. Apple says manifest permissions "aren't automatically granted" ([WWDC26 session 8015](https://developer.apple.com/videos/play/wwdc2026/8015/)). So approach (a) is no smoother than (b) on Safari. Every subdomain and custom domain is a site the user must allow in the toolbar popover, and a grant applies across all profiles from Safari 17 on ([Apple](https://developer.apple.com/documentation/safariservices/managing-safari-web-extension-permissions)).

Three Safari questions remain open because no source answered them. What UI does a `permissions.request` for one exact origin show? Is a grant from that call permanent? And does Safari require the origin to be declared in `optional_host_permissions` before it can be requested? Bug 290508 makes the Safari manifest a separate decision, and testing on Safari 18.x and 26.x should come before any Safari release.

## Recommendation and implementation sketch

Adopt a **hybrid of (a), (b) and (d)**, with a Safari-specific manifest. Keep `https://*.schoology.com/*` and the known custom domains (`schoology.npchristian.org`) as required `host_permissions` and static content-script matches. This covers most families with no prompts on Chrome, Edge and Firefox. Adding NPC now costs little, while the user base is small. Do not keep growing that list. For every other school, on Chrome, Edge and Firefox, declare `optional_host_permissions: ["https://*/*"]` and request exactly one origin. The request comes either from the popup ("Use Schoology Dashboard on this site", shown after an `activeTab` fingerprint probe passes) or from an options field where the family types the school's address. For Safari, leave out the wildcard optional permission because of bug 290508. Rely on the static list, Safari's own toolbar grant for listed hosts, and `activeTab` for a one-off read of an unlisted school, until a test shows that an exact-origin request works without the wildcard. Separately, make Safari's refresh run from an open Schoology tab rather than from the service worker, because of bug 260676. This design never asks for "all websites." Every site access the user sees names their school, and adding a new school needs no store release and triggers no Chrome re-approval.

The changes to the `multi-domain` branch are small. `sites.js` stays pure. `isSchoologySite` and `siteForPage` take the granted custom hosts as an argument, so a page on a user-added school counts as `'other'`/`'same'` instead of `'ignore'`. The parent-over-student rule needs no change.

```js
// sites.js (pure)
export const SCHOOL_HOSTS = ['schoology.npchristian.org'];          // built-in, in manifest
const NOT_APP = /^(asset-cdn|files-cdn|api|www|ui|developers?|support|info|status)\.schoology\.com$/;
export function isSchoologySite(url, extraHosts = []) {
  let u; try { u = new URL(url); } catch { return false; }
  if (u.protocol !== 'https:') return false;
  const h = u.hostname.toLowerCase();
  if (NOT_APP.test(h) || h === 'schoology.com') return false;
  return h.endsWith('.schoology.com') || SCHOOL_HOSTS.includes(h) || extraHosts.includes(h);
}
export function siteForPage(pageUrl, base, extraHosts = []) { /* as today, passing extraHosts */ }
// Fingerprint used by the probe and by content.js before doing anything:
export const SCHOOLOGY_FINGERPRINT =
  'link[href*="asset-cdn.schoology.com"],script[src*="/sites/all/themes/schoology_theme/"],' +
  'script[src*="/sites/all/modules/schoology_core/"],#s-user-login-form';
```

```js
// popup.js — inside the click handler, request before any long await
// so the user gesture still counts
async function enableHere(tab) {
  const origin = new URL(tab.url).origin;                       // e.g. https://learn.example.org
  const ok = await chrome.permissions.request({ origins: [`${origin}/*`] });
  if (!ok) return;
  await chrome.scripting.registerContentScripts([{ id: `school:${origin}`,
    matches: [`${origin}/*`], js: ['content.js'], runAt: 'document_idle', persistAcrossSessions: true }]);
  const { extraHosts = [] } = await chrome.storage.local.get('extraHosts');
  await chrome.storage.local.set({ extraHosts: [...new Set([...extraHosts, new URL(origin).hostname])] });
}
// The probe that decides whether to show the button (activeTab + scripting):
// chrome.scripting.executeScript({ target: { tabId }, func: s => !!document.querySelector(s), args: [SCHOOLOGY_FINGERPRINT] })
```

In `background.js`, `maybeAutoRefresh` should load `extraHosts`, pass them to `siteForPage`, and call `chrome.permissions.contains({ origins: [base + '/*'] })` before fetching. If the check fails, because the user withdrew access or Chrome is set to "On click", it should mark the site as needing permission so the popup can ask again, instead of failing silently. A `permissions.onRemoved` listener should unregister the matching content script and drop the host from `extraHosts`. Running `permissions.contains` against the registered scripts at startup keeps the two in sync. The manifest gains `"activeTab"` in `permissions` and `"optional_host_permissions": ["https://*/*"]` for the Chromium and Firefox builds. Firefox needs `browser_specific_settings.gecko.data_collection_permissions` declaring no collection; this is required for new AMO submissions since November 2025 ([Mozilla Add-ons blog](https://blog.mozilla.org/addons/2025/10/23/data-collection-consent-changes-for-new-firefox-extensions/)), and the exact schema value should be checked. The existing unit test that keeps `SCHOOL_HOSTS` and the manifest in sync stays as it is. Only user-added hosts live outside the manifest.

The privacy policy and store listings can then say, accurately: "Schoology Dashboard runs on Schoology sites (`*.schoology.com` and a few schools' own Schoology addresses). If your school uses a different address, the extension asks permission for that one site only, when you click to enable it. It reads your grades pages with your own sign-in. Nothing leaves your browser. You can remove a site at any time in the extension's options or in your browser's site-access settings." The Chrome Web Store justification for the optional wildcard is: "Requested only for the single Schoology address a user enters or enables; required because some schools host Schoology on their own domain." Apple's guideline 5.1.4 on minors' data deserves a re-read before the Safari submission, since students may install the extension.

## Conclusion

The domain question turns out to be less about Schoology than about trust and browser quirks. Recognising Schoology on an arbitrary domain is solved: one `querySelector` is enough. The harder constraints are elsewhere. Chrome re-prompts users for every hard-coded addition. Safari will not grant hosts silently, and its open bugs make the obvious wildcard design noisy and its background fetches unreliable. The custom-domain population is also large and growing (at least 379 hosts) but scattered, so no hand-kept list will ever cover it. The hybrid design keeps the narrow, honest install warning the extension has today, and lets each family supply the one fact the extension cannot look up: the address where they sign in.

Several items remain unverified. They are the Chrome prompt text for an optional origin, Safari's behaviour for an exact-origin request without a wildcard declaration, Schoology's session-cookie SameSite attribute, and whether `*.schoology.com` subdomains share a session. Each can be settled with a signed-in browser in a few minutes, and the Safari test should come first: if exact-origin requests work there without the wildcard, Safari can get the same user-added-school flow as the other browsers.
